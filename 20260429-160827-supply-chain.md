## Open issues

### Workflow token permissions (6)

The default `GITHUB_TOKEN` ships with `contents: write` for same-repo events when no `permissions:` block is declared. Each unscoped workflow grants any compromised step the ability to push code, mint releases, and (on workflows with `id-token: write`) vend OIDC tokens to external services. The fix is uniform: add `permissions: read-all` at the workflow level, then escalate per job only where needed.

- `.github/workflows/ci.yaml:1` — workflow lacks a top-level `permissions:` block. Recommend `permissions: read-all` (no job needs write).
- `.github/workflows/integration-tests.yaml:1` — workflow lacks a top-level `permissions:` block. Recommend `permissions: read-all` (no job needs write).
- `.github/workflows/release.yaml:1` — workflow lacks a top-level `permissions:` block. The `release` job already declares `contents: write` at line 11; add `permissions: read-all` at the workflow level so any future job inherits read-only.
- `.github/workflows/fossa.yml:10` — top-level `id-token: write`. Legitimate (used by `rancher-eio/read-vault-secrets` to authenticate to Vault), but scope it to the `fossa-scanning` job rather than the whole workflow.
- `.github/workflows/release.yaml:12` — job-level `contents: write`. Legitimate (`gh release create` needs it). The mechanical finding is correct; surface it here so the matching workflow-level `permissions: read-all` lands in the same fix.
- `.github/workflows/renovate-vault.yml:21` — top-level `id-token: write`. Legitimate (Vault auth). Move to the `call-workflow` job for least-privilege.

## Retro: dependency types not explicitly covered

The scan surfaced no manifest formats outside the script's table, and no Phase 2 judgment ran into a case the rules couldn't classify. Two minor observations worth filing for the queue:

1. **`sha512sum --check` long-form flag.** The Phase 2 rules document `sha512sum -c` but `scripts/install-envtest.sh:39` uses `sha512sum --check`. The script accepted it (the inline-download verifier was marked ✓), so this is presumably already handled — but the rule text under "Inline downloads" (step 4) should mention long-form `--check` alongside `-c` so the next reader knows it's intentional rather than coincidental.

2. **Reusable workflow `uses:` references.** `.github/workflows/renovate-vault.yml:25` invokes `rancher/renovate-config/.github/workflows/renovate-vault.yml@<sha>` — a SHA-pinned reusable workflow. The script counted it under the GHA total and treated it as pinned, which is correct. Worth a one-line confirmation in the Phase 1 docs that `<owner>/<repo>/path/to/workflow.yml@<sha>` is in scope of the same `uses:` rule, since reusable-workflow refs look superficially different from action refs.
